# CS2 Nade Studio

Application compagnon Windows pour consulter et créer des lineups de grenades CS2 sur un écran secondaire. Voir `docs/` pour le détail complet ; ce fichier ne couvre que ce qu'il faut garder en tête à chaque session.

## Structure du repo (monorepo)

```
app/       Application Python + pywebview (fenêtre principale + overlay de création)
plugin/    Plugin CounterStrikeSharp en C# (serveur CS2 dédié local)
docs/      Documentation détaillée (voir ci-dessous)
```

## Documentation détaillée

- `docs/structure-donnees-lineups.md` — modèle de données (Map, Lineup, Waypoint)
- `docs/architecture-technique-lineups.md` — vue d'ensemble des composants et de leurs échanges
- `docs/structure-plugin-cs2sharp.md` — structure interne du plugin
- `docs/installation-locale.md` — installation du serveur dédié, Metamod, CounterStrikeSharp

Toujours consulter le document pertinent avant de modifier une zone qu'il couvre, plutôt que de redéduire l'architecture depuis le code seul.

## Contraintes à respecter systématiquement

- **Windows uniquement.** Ne pas ajouter de code ou de dépendance spécifique à Linux/macOS.
- **Thread safety côté plugin** : toute lecture ou modification d'entité (position, téléportation) déclenchée depuis le serveur HTTP embarqué doit passer par `Server.NextFrame(...)`. Jamais d'accès direct aux entités depuis le thread HTTP.
- **Pas de fenêtre transparente.** `pywebview` ne supporte pas `transparent=True` de façon fiable sous Windows. L'overlay de création est un petit panneau opaque positionné dans un coin de l'écran (`frameless=True`, `on_top=True`), pas un calque transparent superposé au jeu.
- **Capture d'écran via `mss`**, jamais via le jeu ou le plugin — le serveur n'a aucun accès au rendu du client, c'est une limite architecturale et non une fonctionnalité à chercher à contourner.
- **Déclenchement au clavier, pas au clic**, pendant la création en jeu : les actions (`capturer`, `tester`) passent par des raccourcis globaux (`keyboard.add_hotkey`), car le focus reste sur la fenêtre CS2 pendant le jeu.
- **Un seul joueur humain supposé** sur le serveur local — pas besoin de gérer plusieurs joueurs simultanés côté plugin pour l'instant.
- **Aucune fonctionnalité basée sur la lecture ou la téléportation de position en dehors du serveur local.** Le plugin n'existe que là où vous l'installez vous-même ; sur un serveur de matchmaking ou non contrôlé, cette donnée n'est techniquement accessible nulle part. Ne jamais proposer ou implémenter une fonctionnalité qui présupposerait l'accès à la position d'un joueur pendant une vraie partie.

## Canal application ↔ plugin

HTTP local, port 5050 par défaut (configurable si conflit) :
- `GET /position` → position et angle de vue actuels du joueur
- `POST /teleport` → déplace le joueur vers une position et un angle donnés

## Point de friction récurrent : mise à jour CS2 peut bloquer le serveur au démarrage

Après une mise à jour Steam/CS2, le serveur peut se bloquer silencieusement juste après le chargement de CounterStrikeSharp (aucune erreur, aucun crash, juste plus aucune ligne de log — reste bloqué avant même d'ouvrir le port réseau du jeu, CPU actif mais mémoire figée).

**Ne pas supposer que c'est Metamod sans vérifier** : une première investigation avait conclu à une incompatibilité Metamod:Source ↔ nouveau moteur, mais **c'était une fausse piste** — Metamod et CounterStrikeSharp démarraient en fait très bien seuls ; c'est notre propre plugin (`HttpApiServer.HandleRequestsAsync`) qui bloquait le jeu, voir "Blocage causé par notre propre plugin" ci-dessous.

**Méthode de diagnostic fiable, par bisection** (retirer une couche à la fois et relancer) :
1. Retirer notre plugin (`counterstrikesharp/plugins/LineupCapturePlugin`, le déplacer ailleurs temporairement) en gardant Metamod + CS# → si ça démarre, le problème vient de notre plugin, pas de Metamod/CS#.
2. Si le problème persiste sans notre plugin, retirer aussi la ligne `Game csgo/addons/metamod` de `game/csgo/gameinfo.gi` → si ça démarre sans Metamod, c'est bien une incompatibilité Metamod ↔ moteur (vérifier alors `https://api.github.com/repos/alliedmodders/metamod-source/releases/latest` et les issues du repo).

**Point sans rapport, mais qui peut faire perdre du temps en même temps** : si `connect` échoue avec « client pas à jour », ce n'est pas ce blocage — ça veut dire que le **serveur dédié** (mis à jour manuellement via SteamCMD) est en retard par rapport à la version courante du jeu. Le client Steam de l'utilisateur se met à jour automatiquement et est toujours à la bonne version (confirmé : connexion aux serveurs officiels fonctionne normalement) ; c'est donc le serveur dédié local qu'il faut remettre à jour via SteamCMD (`+app_update 730 validate`).

**Fausse piste précédente, corrigée le 15 août 2026** : après la mise à jour CS2 du 15 août 2026, une bisection avait conclu à une incompatibilité CS# ↔ nouvelle version du jeu, non résolue par les mainteneurs (`[META] Loaded 0 plugins.`, rattachée à l'issue [#1365](https://github.com/roflmuffin/CounterStrikeSharp/issues/1365)). **Cette conclusion était fausse.** En comparant notre installation aux instructions officielles (`INSTALL.md`/wiki AlliedModders), la vraie cause est un défaut de notre propre installation : le fichier `counterstrikesharp.vdf` (livré par l'archive « with runtime » de CS#) se retrouvait à la racine de `game/csgo/addons/` au lieu de `game/csgo/addons/metamod/`. Or Metamod ne scanne que **son propre dossier** (`addons/metamod/`, ou `mm_basedir`) pour découvrir automatiquement les plugins via leurs `.vdf` — un `.vdf` mal placé est ignoré silencieusement, sans erreur ni ligne `CSSharp:` dans les logs, ce qui imite parfaitement un échec de chargement natif. **Correctif validé en conditions réelles** : déplacer `counterstrikesharp.vdf` vers `addons/metamod/counterstrikesharp.vdf` → `[META] Loaded 1 plugin.`, CS# et notre plugin chargent normalement, `curl /position` répond. Voir `docs/installation-locale.md` (étape mise à jour). Aucune incompatibilité moteur réelle n'a jamais existé sur ce projet ; l'issue #1365 reste possiblement pertinente pour d'autres causes, mais pas pour ce symptôme précis vu ici.

**Piste écartée en cours de route** : les Visual C++ Redistributables (requis sur Windows selon `INSTALL.md`) étaient déjà installés et à jour (v14.44.35211) — pas la cause.

**Cause racine identifiée (à ne plus reproduire)** : `+force_install_dir` était passé avec un chemin **relatif contenant `..`** (`../cs2server`) — un bug documenté de SteamCMD (pas spécifique à ce projet, ni à l'update, ni au fait que ce soit un `app_update` plutôt qu'une install initiale) : les chemins relatifs avec `..` ne sont pas fiablement résolus et SteamCMD retombe silencieusement sur `steamcmd/steamapps/common/Counter-Strike Global Offensive/game`. **Toujours utiliser un chemin absolu** (ex. `D:\Documents\Github\cs2server`) pour `force_install_dir`, à l'install initiale comme à chaque mise à jour — voir `docs/installation-locale.md`. Ordre des commandes (`force_install_dir` avant `login`) n'était pas en cause, il était déjà correct.

**Si le piège survient quand même** (ancien script/habitude réutilisant un chemin relatif) : ne pas juste écraser l'ancien dossier `game/` : il contient nos ajouts (Metamod, CounterStrikeSharp, notre plugin, `gameinfo.gi` édité, `cfg/gamemode_competitive_server.cfg`, `cfg/prac.cfg`) qui ne font pas partie du dépôt Steam. Procédure sûre : renommer l'ancien `game/` de côté, déplacer le nouveau à sa place, puis recopier ces ajouts par-dessus depuis l'ancien dossier.

## Blocage causé par notre propre plugin : continuations async captées sur le thread principal

Après une mise à jour CS2, `HttpApiServer.HandleRequestsAsync()` (la boucle `await _listener.GetContextAsync()` lancée en fire-and-forget depuis `Load()`, donc démarrée sur le thread principal du jeu) bloquait tout le jeu dès qu'elle recevait une requête — confirmé par bisection en conditions réelles (`_listener.Start()` seul : OK: la boucle de traitement ajoutée : blocage). Cause probable : une continuation `await` qui tente de reprendre sur le contexte capturé au moment du `Load()` (thread principal), ce qui n'était pas un problème sur l'ancienne version du moteur mais l'est devenu avec celle-ci.

**Solution** : `.ConfigureAwait(false)` sur absolument tous les `await` de `HttpApiServer.cs`, pour que les continuations reprennent sur un thread du pool plutôt que de tenter de revenir sur le thread principal. Revalidé avec `curl` (200 sur `/position` et `/teleport`) après correctif.

Ne pas oublier au passage : `gameinfo.gi` est aussi entièrement réécrit par certaines mises à jour CS2 (perd la ligne du hook Metamod) — à vérifier/rajouter séparément de ce point de compatibilité.

## Points résolus

- **Positionnement précis d'une fenêtre `pywebview`** : les kwargs `x`/`y` de `webview.create_window(...)` suffisent pour positionner l'overlay au chargement (voir `app/main.py`, calcul via `ctypes.windll.user32.GetSystemMetrics` pour la résolution d'écran). Aucun fallback `pygetwindow`/`win32gui` nécessaire pour ce cas d'usage.
- **`Server.NextFrame` et thread safety** : confirmé fonctionnel en conditions réelles (build + déploiement + `curl /position` et `/teleport`, réponses HTTP 200 correctes). `Server.NextFrame` utilise en interne une `ConcurrentQueue`, donc l'appeler depuis le thread HTTP est sûr.
- **Version du SDK .NET requise pour le plugin** : `CounterStrikeSharp.API` (à partir de la 1.0.371) cible `net10.0`, pas `net8.0` comme supposé initialement dans `structure-plugin-cs2sharp.md` — `plugin/LineupCapturePlugin/LineupCapturePlugin.csproj` a été corrigé en conséquence. À revérifier si CounterStrikeSharp change de TFM dans une future version.
- **Angle de vue réel du joueur (lecture)** : `pawn.EyeAngles` (« current view angle ») est la bonne propriété, pas `pawn.AbsRotation` (qui ne reflète que l'orientation du corps — le pitch y restait à 0 quel que soit le regard vertical, confirmé en jeu). Vérifié par un test réel : `EyeAngles.X`/`EyeAngles.Y` correspondent exactement au `setang` renvoyé par la commande console `getpos`, y compris en visant fortement vers le haut/bas. Voir `HttpApiServer.GetCurrentPosition()`.
- **Décalage de `Z` entre `AbsOrigin` et `getpos`** : `pawn.AbsOrigin.Z` correspond aux pieds du joueur, alors que `getpos` (comme un lancer de grenade réel) reflète la position des yeux — écart constaté d'environ 63 unités en position debout. Sans impact pour cet usage (voir point suivant, la téléportation ne passe plus par `AbsOrigin`/`Teleport()` de toute façon).
- **Téléportation avec un pitch précis (écriture)** : `pawn.Teleport(position, angle, vélocité)` fait pencher tout le corps/hitbox du joueur dès que l'angle contient un pitch non nul — confirmé comme une limitation du moteur CS2 actuel lui-même (reproduit à l'identique avec **SharpTimer**, plugin de référence en production massivement utilisé ; bug ouvert et non résolu à ce jour : [poor-sharptimer#133](https://github.com/Letaryat/poor-sharptimer/issues/133)). Ni l'écriture directe sur `V_angle`/`EyeAngles`, ni un second appel `Teleport(angles: ...)` différé d'un tick (technique du plugin `CS2-TeleportAnglesFix`, qui ne fonctionne que pour de petites corrections d'angle) n'ont résolu le problème. **La solution qui fonctionne** : exécuter `setpos`/`setang` comme des commandes client (`player.ExecuteClientCommandFromServer("setpos X Y Z")` puis `"setang PITCH YAW 0"`), exactement comme si le joueur les tapait dans sa propre console — un chemin de code natif différent de `Teleport()`, qui ne présente pas ce défaut. Nécessite `sv_cheats 1` sur le serveur (voir point suivant). Voir `HttpApiServer.TeleportPlayer()`.
- **`sv_cheats 1` réinitialisé par le gamemode compétitif** : le mode de jeu compétitif exécute son propre config après le lancement du serveur et remet `sv_cheats` à `0`, même si `+sv_cheats 1` est passé en ligne de commande. Contournement : créer `game/csgo/cfg/gamemode_competitive_server.cfg` (hook optionnel que le jeu tente déjà de charger après `gamemode_competitive.cfg`) avec `sv_cheats 1` dedans.
- **Capture d'écran limitée à la fenêtre du client CS2** : `mss.mss().shot(mon=-1, ...)` capture tout l'affichage combiné (tous les écrans) — pas ce qu'on veut. Localiser la fenêtre CS2 via `ctypes` (`EnumWindows` + titre exact `"Counter-Strike 2"`), en excluant le serveur dédié local qui crée lui aussi une fenêtre du même titre (vérifier que `-dedicated` n'est pas dans la ligne de commande du processus propriétaire, via `psutil.Process(pid).cmdline()`).
  **Piège découvert ensuite, en conditions réelles** : capturer uniquement la bonne *région d'écran* (`GetClientRect` + `ClientToScreen`, puis `mss().grab(region)`) ne suffit pas — CS2 tourne en plein écran **sans bordure**, pas en exclusif, donc d'autres fenêtres (notre propre overlay, la console du serveur dédié, la barre des tâches, une appli au premier plan) peuvent physiquement se superposer aux mêmes pixels d'écran, et un grab par région les capture aussi (`mss.grab` ne connaît que des coordonnées écran, pas la notion de fenêtre). Confirmé visuellement : un screenshot capturé pendant un test montrait le jeu + la console du serveur dédié + l'overlay + la barre des tâches, tous superposés.
  **Solution qui fonctionne** : `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` (rendu direct du contenu de cette fenêtre précise par DWM, indépendant de ce qui est visuellement au-dessus), suivi de `GetDIBits` pour extraire les pixels bruts, convertis en RGB puis passés à `mss.tools.to_png(...)` (mss reste utilisé pour l'encodage PNG, conformément à la contrainte d'architecture — seule la méthode de capture des pixels change). Voir `_capture_window_rgb()` dans `app/core/capture.py`.
- **Assets radar (images + calibration)** : sourcés depuis [`MurkyYT/cs2-map-icons`](https://github.com/MurkyYT/cs2-map-icons), qui extrait automatiquement les images radar et les données de calibration (`pos_x`, `pos_y`, `scale`) directement depuis le dépôt de jeu de Valve, mis à jour à chaque update CS2. Périmètre retenu : le pool competitive actif (Premier, 7 cartes) + les cartes récemment dans ce pool — 10 au total (mirage, ancient, inferno, dust2, nuke, anubis, overpass, train, vertigo, cache), voir `app/data/maps.json` et `app/assets/radar/`. Formule de transformation monde ↔ pixel (image 1024×1024) : `px = (x - radarPosX) / radarScale`, `py = (radarPosY - y) / radarScale` (axe Y inversé). Nuke a un niveau inférieur avec son propre radar, non géré pour l'instant (une seule image par carte).
- **Masquer le HUD pendant une capture (`HideHUD`) — résolu** : quatre mécanismes serveur→client testés en premier, tous sans effet malgré aucune exception :
  1. `player.ExecuteClientCommandFromServer("cl_crosshairsize ...")` — ne fait que `DispatchConCommand` sur la table de commandes du **serveur**, qui ne connaît pas les convars `cl_*` (jamais répliquées).
  2. Entité `point_clientcommand` (technique des cartes custom type « crashz' Crosshair Generator ») — nécessite du contenu client embarqué (Panorama UI livré avec la carte) que notre plugin ne peut pas fournir.
  3. `GameEvent` synthétique (`weapon_fire`/`player_hurt`) via `FireEventToClient` — aucun effet non plus.
  4. `player.ReplicateConVar(...)` (vrai message réseau `CNETMsg_SetConVar`, voir `natives_commands.cpp`) — fonctionne pour de vraies convars serveur (`mp_maxmoney`, `sv_disable_radar`...) mais pas seul pour le rafraîchissement HUD.
  **Cause racine, trouvée dans un exemple de code tiers** : modifier `pawn.HideHUD` via le setter C# change la mémoire côté **serveur** (d'où une lecture cohérente via un endpoint `/capture/check` dédié, resté stable en continu sur plusieurs secondes de sondage) mais ne force pas le moteur Source 2 à **réseauter** cette valeur au client — sans le signaler explicitement, le champ n'est simplement jamais envoyé. `Utilities.SetStateChanged(pawn, "CBasePlayerPawn", "m_iHideHUD")` force cette propagation immédiatement — confirmé en conditions réelles : masquage total (minimap, viseur, armes, munitions, temps, scoreboard) **instantané**, plus besoin d'aucun délai d'attente. L'argent restait visible avec `HideHUD` seul (non couvert par ce champ en CS2) — masqué en complément via `player.ReplicateConVar("mp_maxmoney", "0")` (convar serveur légitime, restaurée à sa vraie valeur via `ConVar.Find("mp_maxmoney")` au moment de `RestoreCapture`). Voir `PrepareCapture()`/`RestoreCapture()` dans `HttpApiServer.cs`.
  Le viseur du jeu étant masqué avec le reste, l'app dessine son propre viseur (magenta, toujours au centre exact de l'image) sur le screenshot, plus un crop zoomé (`screenshotZoomRef` sur `Waypoint`) — voir `_draw_crosshair()`/`_take_screenshot()` dans `app/core/capture.py`.
  Intégré automatiquement dans le flux F9 → capture (délai de sécurité de 0.1s seulement). Un bouton « Masquer le HUD (test) » reste disponible dans la fenêtre principale (`Api.toggle_hud()`) pour un déclenchement manuel ponctuel.
  **Complément — grenades en vol, fumée, feu** : masqués/supprimés eux aussi pendant une capture, via un `RegisterListener<Listeners.CheckTransmit>` dans `LineupCapturePlugin.Load()` qui appelle `.Remove()` (pas juste un masquage de transmission) sur toutes les entités dont le `DesignerName` correspond à `smokegrenade_projectile`, `hegrenade_projectile`, `flashbang_projectile`, `decoy_projectile`, `molotov_projectile`, `inferno` — technique de base reprise du TestPlugin officiel CounterStrikeSharp (masquage de `prop_door_rotating` via `CheckTransmit`/`TransmitEntities`), mais suppression complète plutôt que simple masquage : masquer seulement la transmission ne suffit pas pour un nuage de fumée ou un feu déjà déclenché — ce sont des effets particules joués **une fois** côté client dès réception de l'événement de détonation, et couper la transmission après coup ne les arrête pas rétroactivement (confirmé en conditions réelles : un `smokegrenade_projectile` reste la **même entité** après détonation, pas remplacée). La suppression tourne en **continu à chaque tick** tant que la capture est active (pas un seul passage) pour rattraper le feu qui continue de faire apparaître de nouveaux segments `inferno` en se propageant. Pas de restauration cherchée (un screenshot n'a pas besoin que ces objets survivent après coup) — sans conséquence pour d'autres joueurs (un seul joueur humain supposé, voir plus haut dans ce fichier).
  Une route de diagnostic `/debug/entities?contains=...` (liste les entités dont le nom contient un mot-clé donné) a servi à identifier empiriquement les bonnes entités plutôt que deviner depuis la documentation — `_firesmoke` et `info_particle_system` (trouvées dans un dump générique de la liste d'entités CS2) se sont révélées inutiles ici : seule `inferno` existe réellement pour le feu d'un molotov sur ce build.
  **Limite résiduelle acceptée** : un léger fondu visuel reste visible à l'extinction du feu d'un molotov, même avec la suppression continue — confirmé via `/debug/entities` qu'**aucune entité** feu/flamme/particule n'existe plus à ce moment (l'entité `inferno` est déjà supprimée) : c'est un pur fondu client, indépendant de toute entité serveur, donc rien à supprimer de plus. Accepté tel quel — la fumée, elle, disparaît instantanément.
  **Complément — trajectoire et caméra de grenade** : la caméra qui suit une grenade lancée, l'aperçu de trajectoire, la ligne de trajectoire une fois lancée et les impacts de balle en surbrillance (utiles en pratique normale, mais polluent un screenshot de lineup) sont contrôlés par de vraies convars **serveur** (sv_cheats) — répliquées normalement à tous les clients par le moteur. `sv_grenade_trajectory` **n'existe pas** sur ce build CS2 malgré plusieurs sources en ligne qui la mentionnent (confirmé en jeu : « n'existe pas » en console) — `ConVar.Find` la retourne silencieusement à `null`, sans erreur. Le masquage repose entièrement sur `sv_grenade_trajectory_prac_pipreview`, `sv_grenade_trajectory_prac_trailtime` (mis à `0`) et `sv_showimpacts` — **confirmé en jeu : masque bien la caméra de suivi, l'aperçu, la ligne de trajectoire post-lancer et les impacts, les quatre à la fois.** Lues/écrites via la propriété `StringValue` (pas `GetPrimitiveValue<bool>()`/`SetValue(bool)` — a échoué silencieusement pour `sv_grenade_trajectory_prac_pipreview`, probablement un type interne non-bool). État d'origine (HideHUD + dictionnaire de ces convars) regroupé dans `Models/CaptureState.cs`, transporté tel quel entre `/capture/prepare` et `/capture/restore`.
  **Bug connu, non résolu, mis de côté pour l'instant** : la restauration après capture ne fonctionne plus de façon fiable — observé en conditions réelles : ni `HideHUD` (contournable par un `kill`/respawn, qui réinitialise le pawn) ni les convars `sv_grenade_trajectory_prac_*`/`sv_showimpacts` ne reviennent à leur valeur d'origine après `/capture/restore`. Cause non investiguée (mis de côté à la demande de l'utilisateur) — à reprendre : vérifier si `RestoreCapture` lève une exception silencieuse, si le pawn a changé entre `prepare` et `restore` (mort/respawn pendant la capture), ou si `StringValue` a le même problème de propagation réseau que `pawn.HideHUD` avant le fix `SetStateChanged` (auquel cas il faudrait aussi un `SetStateChanged` ou équivalent pour ces convars).
- **Chargement des images radar dans pywebview** : un chemin relatif remontant les dossiers (`../../assets/...`) depuis `index.html` échoue silencieusement (image cassée) — le serveur local que pywebview utilise pour servir les fichiers bloque la remontée de dossiers (`..`). Solution : une méthode d'API (`Api.get_asset_data_url` dans `app/main.py`) lit le fichier côté Python et renvoie un data URI base64, chargé ensuite via `img.src` en JS (`setRadarImageSrc` dans `main.js`) — fonctionne quel que soit le comportement du serveur de fichiers interne.
- **Radar qui remplit l'espace disponible sans le déborder** : pas de solution CSS pure fiable pour "le plus grand carré qui rentre dans une zone flexible" (l'association `aspect-ratio` + `flex`/`grid` ne suffit pas). Solution : mise en page flex (`#view-browse` en colonne pleine hauteur, `.radar-row` en `flex:1`), puis en JS (`fitRadarSquares` dans `main.js`) on mesure le rectangle alloué par la mise en page et on réduit le radar au plus grand carré qui y rentre, recalculé au redimensionnement de la fenêtre.
- **Hibernation du serveur dédié sans joueur connecté** : quand aucun joueur n'est connecté, CS2 réduit fortement la fréquence de tick du thread principal (`sv_hibernate_when_empty`, activé par défaut), ce qui peut faire tarder voire expirer les requêtes `/position`/`/teleport` (la file `Server.NextFrame` ne se vide qu'au tick suivant). Pour tester l'API sans joueur connecté, lancer le serveur avec `+sv_hibernate_when_empty 0`. En usage réel (un joueur connecté pendant la capture), ce n'est pas un problème. `HttpApiServer` a par ailleurs été durci pour renvoyer une erreur HTTP 500 après 5s plutôt que de bloquer indéfiniment si le thread principal ne répond pas.
